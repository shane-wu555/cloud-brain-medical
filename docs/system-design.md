# 智慧云脑诊疗平台系统设计文档

## 1. 系统总体介绍

智慧云脑诊疗平台面向医院门诊诊疗场景，覆盖患者就诊前、就诊中、就诊后以及医院内部运营管理流程。系统由患者端小程序、医院工作人员 PC Web、Spring Boot 后端微服务、FastAPI AI 智能服务和基础设施组件组成，实现从实名建档、AI 问诊、预约挂号、候诊叫号、医生接诊、检查检验、报告确认、处方缴费、药房发药、退费退药、排班管理到审计追踪的闭环。

平台的核心设计目标是把传统门诊流程拆分为边界清晰的业务服务，并在关键节点引入 AI 辅助能力，但所有 AI 结果均保持“草稿/建议”属性，需要由授权医务人员确认后才进入正式业务流程，符合医疗系统对安全性、可追溯性和人工责任边界的要求。

## 2. 总体架构

系统采用前后端分离与微服务分层架构。

用户交互层包含两类入口：

- 患者端：`patient-miniapp/`，基于 uni-app、Vue 3、TypeScript，面向微信小程序发布，提供登录、实名、问诊、挂号、缴费、病历、医嘱、处方、报告等患者自助功能。
- 工作人员端：`frontend/`，基于 Vue 3、TypeScript、Pinia、Vue Router、Axios、Element Plus、ECharts，按角色提供门诊医生、医技医生、检验医生、处置医生、药房、收费员、管理员和审计页面。

接入层由 `gateway-service` 统一承载，使用 Spring Cloud Gateway 对 `/api/**` 请求进行路由。网关监听 `8080`，路由到认证、患者、医生排班、挂号、收费、药房、病历、医嘱、审计和 AI 服务。

业务微服务层位于 `backend/`，采用 Maven 多模块 Spring Boot 3.3.6 + Java 17。后端模块包括：

- `common`：通用 API 错误、角色码、审计事件模型。
- `gateway-service`：统一网关与 JWT 资源服务安全入口。
- `auth-service`：注册、登录、短信验证码、密码重置、员工账号、RBAC。
- `patient-service`：患者档案、绑定关系、通知中心、内部患者校验。
- `doctor-service`：科室、医生、诊室、排班、号源同步、AI 排班建议。
- `appointment-service`：挂号、号源库存、候诊队列、复诊、集成事件。
- `cashier-service`：支付订单、退款订单、窗口收费、扫码入口。
- `medical-record-service`：电子病历、报告回写、访问日志。
- `medical-order-service`：检查、检验、处置医嘱，附件、报告、AI 影像任务。
- `pharmacy-service`：药品目录、处方、发药、退药、库存与库存预测。
- `report-service`：报告服务基础能力。
- `audit-service`：审计日志接收、查询、Elasticsearch 检索索引。

AI 智能服务层位于 `ai-service/`，采用 FastAPI，统一挂载在 `/api/ai` 前缀下，提供智能问诊、分诊、医生推荐、临床辅助、CT 分析、报告草稿、处方建议、知识库检索与排班建议。

数据与基础设施层由 `docker/docker-compose.yml` 定义，包含 PostgreSQL + pgvector、Redis、RabbitMQ、MinIO、Elasticsearch。后端各服务使用 PostgreSQL 独立 schema 与 Flyway 迁移管理数据结构；Redis 用于账号/患者缓存和部分业务缓存；RabbitMQ 用于审计事件发布与消费；MinIO 保存医技附件；Elasticsearch 支撑药品和审计日志检索；pgvector 支撑 AI RAG 知识库。

## 3. 关键业务流程设计

### 3.1 认证与权限流程

认证模块由 `auth-service` 实现，提供注册、账号密码登录、短信验证码发送、短信登录、密码重置、密码修改和员工账号管理接口。系统使用 Spring Security OAuth2 Resource Server 解析 JWT，前端路由也通过角色元信息进行二次控制。

工作人员端路由按角色隔离：

- `OUTPATIENT_DOCTOR` 进入门诊医生工作台。
- `CHECK_DOCTOR`、`LAB_DOCTOR` 进入医技/检验工作台。
- `DISPOSAL_DOCTOR` 进入处置工作台。
- `PHARMACY_STAFF` 进入药房工作台。
- `CASHIER` 进入收费工作台。
- `ADMIN` 进入管理与审计页面。

设计重点是前端角色路由、网关 JWT 验证、服务内 `@PreAuthorize` 和内部接口 `X-Internal-Api-Key` 多层配合。普通用户接口、工作人员接口和服务间内部接口不混用同一信任边界。

在一个很小的登录流程中，系统会先由 `AuthController` 接收登录请求，`AuthService` 校验账号与密码，再由 `TokenService` 生成带角色信息的 JWT。工作人员端拿到 token 后，Pinia 保存登录态，Vue Router 根据角色把用户带到对应工作台。例如 `CASHIER` 进入收费台，`PHARMACY_STAFF` 进入药房工作台，`OUTPATIENT_DOCTOR` 进入门诊医生工作台。这个流程的特点是“登录结果直接决定岗位入口”，避免所有角色进入同一个后台后再手动寻找菜单。

员工账号管理也是权限模块的细节之一。管理员可以创建员工账号、修改基本信息、重置密码和启停账号。账号启停不是删除数据，而是改变账号可用状态，这样既能满足人员离岗后的权限回收，也能保留历史审计记录中对应的操作者身份。

内部接口的权限设计也体现在很多小流程中。例如支付成功后，收费服务回调挂号服务或医嘱服务时，不走普通用户 token，而是携带 `X-Internal-Api-Key` 调用 `/api/internal/**` 接口。这说明系统把“用户主动操作”和“服务间业务推进”分成两种调用来源，减少越权调用风险。

### 3.2 患者就诊入口流程

患者端小程序包含首页、登录、实名、个人资料、搜索、AI 问诊、预约挂号、挂号记录、待缴费、检查检验/处置、处方、病历、就诊记录等页面。患者通过小程序完成账号登录、患者档案绑定、AI 问诊、科室/医生选择、在线挂号和支付。

`patient-service` 负责维护患者档案与账号绑定关系，同时提供内部校验接口给挂号、医嘱、药房等服务使用，避免各业务服务重复实现患者归属判断。通知中心支持未读数量、通知列表、单条已读和全部已读，并由其他服务通过内部接口写入业务通知。

患者实名建档可以拆成一个很小的流程：患者先登录账号，再在小程序中填写或绑定患者资料，系统将账号 ID 与患者档案 ID 建立绑定关系。后续患者查看病历、报告、处方或医嘱时，业务服务不会只相信前端传来的患者 ID，而是通过 `patient-service` 的内部接口校验该账号是否拥有对应患者档案。这个细节解决了患者端最常见的越权访问问题。

通知中心贯穿多个流程。例如挂号成功、报告发布、处方待缴费、药房发药等动作完成后，相关业务服务可以通过患者服务的内部通知接口写入通知。患者端再通过未读数量接口和通知列表展示结果。这个设计让通知不散落在各业务服务中，而是统一沉淀在患者服务，便于患者端形成一致的消息体验。

AI 问诊在患者入口处承担“就诊前信息整理”的作用。患者提交主诉和症状后，AI 服务生成症状摘要、风险提示和科室建议，患者再进入挂号流程。这里的特色不是让 AI 替代诊断，而是把患者零散描述整理成结构化上下文，为后续医生接诊和科室选择提供辅助。

### 3.3 挂号、号源与候诊流程

医生与排班基础数据由 `doctor-service` 管理，挂号交易和候诊队列由 `appointment-service` 管理。排班发布后，医生服务通过号源同步能力将半天粒度排班转换为预约号源库存；挂号服务维护 `slot_inventory` 和 `appointment`，提供号源查询、线上挂号、线下挂号、支付、取消、复诊、过号、叫号、开始接诊等接口。

该流程的关键设计是将“医生排班”和“挂号库存”拆成两个服务：医生服务负责可出诊性和排班管理，挂号服务负责交易状态和库存扣减。服务间通过内部接口同步号源，使排班调整和挂号交易可以分别演进。

挂号服务还包含可靠集成事件 `integration_event`，通过定时调度派发电子病历初始化、报告回写等跨服务动作。该设计避免主交易因下游服务暂时不可用而失败，同时提供失败事件查询与重试入口。

号源生成是挂号模块中很小但关键的流程。管理员在 `doctor-service` 发布某医生某日期上午或下午的排班后，系统不会让患者直接预约这个半天排班，而是同步到 `appointment-service` 生成可扣减的号源库存。这样医生排班负责“谁能出诊”，挂号库存负责“还能挂多少号”，两者职责分开。

患者预约时，系统先查询可用号源，再创建挂号记录并进入待支付状态。支付成功后，`cashier-service` 通过内部接口通知 `appointment-service`，挂号记录才推进到有效状态并进入候诊队列。这个小流程体现了“交易状态和支付状态分离”的设计：未支付预约不会直接占用完整就诊流程，支付回调也不会重复推进同一挂号单。

候诊队列支持叫号、过号、开始接诊和复诊。比如医技报告发布后，系统可以让患者回到复诊队列，门诊医生再次看到该患者并继续处理。这使挂号模块不是只做预约表，而是承担门诊现场排队和诊疗节奏控制。

挂号后初始化病历是跨服务可靠事件的典型例子。挂号服务完成本地挂号交易后，写入集成事件；后台调度器再调用病历服务创建初始病历。如果病历服务短暂不可用，挂号不会直接失败，事件会保留并允许重试。这种细节让系统更符合微服务下的最终一致性设计。

### 3.4 医生接诊与电子病历流程

门诊医生工作台由 `frontend/src/views/doctor/DoctorWorkbench.vue` 承载。医生可以查看候诊队列、开始接诊、保存病历、查看正式报告、调用 AI 临床辅助，并发起检查、检验、处置和处方。

`medical-record-service` 负责电子病历的创建、医生初始化、病历记录、归档、历史查询和访问日志。患者只能访问本人已确认数据，门诊医生只能访问授权范围内的病历，管理员可查看访问日志。

设计上，电子病历不是孤立录入表单，而是门诊流程的承接点：挂号可触发初始病历，检查检验正式报告可回写病历，复诊队列可把医技结果带回门诊医生侧，形成“诊疗-检查-复诊”的连续工作流。

门诊接诊可以拆成几个细小动作。医生先在工作台查看今日候诊队列，点击叫号后患者状态改变；点击开始接诊后，系统进入当前就诊上下文；医生填写主诉、现病史、诊断意见等病历内容并保存。保存病历时，系统校验医生角色和就诊关系，避免非当前接诊医生随意写入病历。

医生查看报告也不是直接读取所有报告。患者本人只能看已确认报告，门诊医生只能看自己接诊范围内的正式报告，医技人员只能看自己工作区相关医嘱的附件和报告。这种细节将数据访问范围和岗位职责绑定，符合医疗数据最小授权原则。

AI 临床辅助嵌入在医生工作台内部。医生不是跳转到独立聊天工具，而是在当前患者病历、症状和检查上下文中调用 AI，得到诊断方向、检查建议和风险提醒。医生可以参考这些建议继续开具医嘱，但正式诊断和处置仍由医生在业务系统内保存。

### 3.5 检查检验、附件与报告流程

`medical-order-service` 统一管理检查、检验、处置医嘱。它提供医嘱创建、列表查询、支付确认、叫号、开始、完成、报告待确认、爽约等状态推进接口，同时提供医技工作台数据。

检查和检验附件通过 `MinioStorageService` 存入 MinIO，对象路径按订单维度组织。医技医生可上传附件，发起 CT AI 分析任务，轮询任务状态，并生成报告草稿。`MedicalReportService` 在确认报告时会：

- 校验角色与医嘱类型是否匹配。
- 校验执行人员是否属于对应诊室工作区。
- 使用草稿或人工编辑内容生成正式报告。
- 推进医嘱状态为完成。
- 发布临床工作流事件，回写电子病历。
- 发布审计事件。
- 给患者发送报告发布通知。

AI 生成报告时不会直接成为正式报告，而是保存为 `AI` 来源草稿。医生确认后，如果采用或修改 AI 结果，系统会额外发布 `AI_RESULT_CONFIRMED` 审计事件，记录 AI 任务 ID 和采用状态。

医嘱创建是该模块的起点。门诊医生在接诊时选择检查、检验或处置项目，系统创建医嘱并标记开单医生、患者、项目、执行科室和费用状态。医嘱创建后并不直接进入执行队列，而是需要先完成缴费。缴费成功后，医嘱服务收到内部支付确认，才把医嘱推进到可执行状态。这个细节保证了收费流程和医技执行流程之间的业务边界。

医技执行流程可以细化为“待执行、叫号、开始、上传附件、生成草稿、确认报告”。检查医生先在医技工作台看到已缴费医嘱，叫号后患者进入检查，开始执行后可上传影像、检验单或其他附件。附件通过 MinIO 保存，数据库只保存对象 key、文件名、类型和大小，避免大文件直接进入关系数据库。

CT AI 分析是本模块最有特色的小流程。医生选择某个附件发起 CT 分析，后端调用 AI 服务创建异步任务并保存外部任务 ID。之后工作台轮询任务状态；如果任务完成，系统把 AI 返回的 findings、conclusion、riskAdvice 等内容写成报告草稿；如果任务失败或超时，医生仍然可以人工创建报告草稿。这样 AI 能力增强了报告效率，但不会卡死医技主流程。

报告确认流程体现了医疗 AI 的安全边界。AI 草稿、人工草稿都必须经过医技医生确认才能成为正式报告。确认时系统会校验医生角色是否匹配医嘱类型，例如检查报告需要 `CHECK_DOCTOR`，检验报告需要 `LAB_DOCTOR`。确认后系统推进医嘱完成、回写电子病历、发送患者通知、发布审计事件。如果草稿来源是 AI，还会额外记录医生是否修改过 AI 内容。

### 3.6 收费与退款流程

`cashier-service` 负责支付订单、退款订单、窗口收费查询和扫码入口。业务服务创建支付请求后，收费服务生成支付订单；支付成功或失败再通过内部接口回调挂号、医嘱或药房服务推进业务状态。

该模块的设计重点是将“收款动作”和“业务状态推进”拆开：收费服务只维护支付/退款订单及其回调，业务服务保留自身领域状态。重复支付、失败回调和退款完成都通过服务内状态机保护，避免同一业务单被重复推进。

一个支付小流程是：挂号、医嘱或处方服务先产生待支付业务单；收费服务基于业务单创建支付订单；患者或收费员完成测试支付后，收费服务调用对应业务服务的内部确认接口。业务服务确认该订单仍处于可支付状态后再推进状态。这样即使支付回调重复到达，也不会让同一挂号、医嘱或处方被重复确认。

退款流程同样保持业务归属。例如药房退药会产生退药单和库存回补，再由收费服务处理退款订单；退款完成后通过内部接口通知药房服务更新退药完成状态。这里不是收费服务直接修改药房库存，而是药房服务自己维护库存和退药状态，体现了领域边界清晰的设计。

收费台还提供扫码入口和费用查询能力，方便窗口人员处理线下场景。也就是说系统同时支持患者小程序自助支付和窗口收费员人工处理，适配医院实际存在的线上线下混合收费方式。

### 3.7 药房、处方与库存流程

`pharmacy-service` 提供药品目录、药品检索、入库、处方创建、处方列表、发药、退药、退药单和库存流水能力。处方必须缴费后才能进入发药队列，发药时扣减库存，退药时回补库存并联动退款。

药品检索通过 `DrugSearchIndexService` 对接 Elasticsearch；当 Elasticsearch 不可用时，服务降级到数据库查询，保证业务可用性。库存预测由 `InventoryDemandForecastService` 实现，基于历史发药量、药品单价、需求波动率、提前期和安全库存策略生成推荐预警阈值，并支持定时刷新。

库存预测的模型路由分为三类：

- 高波动药品：采用 Prophet-like 趋势季节性 + XGBoost-like 短期波动的集成策略。
- 中波动药品：采用轻量趋势预测。
- 低波动药品：采用规则化安全库存策略。

当前实现是业务内可解释预测模型，强调可落地和可审计，后续可以替换为真实训练模型而不改变药房业务接口。

处方流转可以拆成一个小流程：门诊医生开具处方后，处方先处于待缴费状态；患者缴费成功后，药房工作台才能看到待发药处方；药师点击发药时，系统逐项检查库存是否充足，库存足够才扣减库存并把处方状态改为已发药。如果库存不足，处方不会被错误推进。这个细节保证了处方状态和真实库存一致。

退药流程也具有完整闭环。只有已发药处方允许发起退药；退药时系统记录退药明细，回补药品库存，并生成退款相关业务动作。这样退药不是简单改变处方状态，而是同时维护处方、退药单、库存流水和退款关系。

药品搜索接入 Elasticsearch，但服务保留数据库兜底查询。当 Elasticsearch 不可用时，药房仍然可以查药、发药和处理库存，只是搜索能力降级。这种小细节体现了医院业务系统对可用性的要求：增强组件可以失败，核心业务不能轻易中断。

库存预测不是只给一个数字。系统会统计一段时间内每种药品的发药数量，计算样本天数、非零需求天数、总需求、平均日需求和波动率，再结合药品价格判断价值层级。高波动药品走集成预测路线，中波动药品走轻量趋势路线，低波动药品走规则安全库存路线。接口返回推荐阈值时同时返回这些中间指标，药房人员可以看懂系统为什么建议调整某个药品的预警线。

### 3.8 审计与检索流程

多个业务服务内置 `AuditPublisher`，通过 RabbitMQ 发布审计事件；`audit-service` 监听并落库，提供审计日志查询和 Elasticsearch 重建索引接口。审计数据覆盖登录、报告确认、AI 结果确认、附件下载、病历访问等敏感行为。

审计服务同样采用“搜索引擎增强 + 数据库兜底”的设计。Elasticsearch 提供高效检索能力，失败时回退数据库查询，确保审计能力不会因为索引服务异常而完全不可用。

审计的一个典型小流程是报告确认。医技医生确认报告后，医嘱服务不仅保存正式报告，还会发布 `MEDICAL_REPORT_CONFIRM` 审计事件；如果该报告来自 AI 草稿，还会发布 `AI_RESULT_CONFIRMED` 事件，记录 AI 任务、报告类型、采用或修改状态。这样后续可以追踪某份报告是人工编写、AI 生成后直接采纳，还是 AI 生成后医生修改采纳。

另一个小流程是附件下载。医生或患者访问检查附件时，系统会校验访问权限，并记录 `MEDICAL_ATTACHMENT_DOWNLOAD` 审计事件，包含附件类型、原始文件名、患者、医嘱和操作者。医疗影像和报告附件属于敏感数据，这种下载级别的审计可以支持后续追责和合规检查。

审计检索同样做了可靠性设计。管理员查询审计日志时，系统优先使用 Elasticsearch 获取更好的检索能力；如果搜索引擎不可用，则回退数据库查询。这样审计页面不会因为索引服务异常完全失效。

## 4. AI 智能服务设计

AI 服务使用 FastAPI，入口文件 `ai-service/app/main.py` 挂载了以下模块：

- `consultation`：患者端多轮问诊与症状摘要。
- `triage`：分诊建议和检查检验建议。
- `doctor_recommendations`：结合症状、风险、医生擅长和可用排班推荐医生。
- `clinical_assistance`：医生端病情摘要、诊断方向、检查建议、风险提醒。
- `ct_analysis`：CT 影像异步分析任务。
- `schedule_suggestions`：管理员排班建议。
- `report_drafts`：根据医技执行数据生成报告草稿。
- `prescription_suggestions`：根据诊断、主诉、过敏史、药品目录生成处方建议草稿。
- `knowledge`：院内 RAG 知识库检索和重建。

### 4.1 大模型接入

`app/core/llm.py` 使用 OpenAI-compatible Chat Completions 接口，支持通过环境变量配置 `AI_OPENAI_BASE_URL`、`AI_OPENAI_API_KEY`、`AI_OPENAI_MODEL` 和超时时间。请求强制设置 `response_format: json_object`，服务收到响应后再进行 JSON 和业务 schema 校验。

错误处理被统一封装为 `LlmError`，FastAPI 全局异常处理器会返回标准错误结构，包含错误码、提示、供应商状态和是否可降级信息。只有显式启用 `AI_ALLOW_FALLBACK=true` 时才允许演示降级，避免生产环境在 AI 不可用时悄悄返回 mock 结果。

一个典型的小流程是报告草稿生成。业务服务把医技执行数据、检查项目、患者上下文和报告要求组装成 JSON 请求，AI 服务在 system prompt 中要求模型只返回 JSON 对象，模型响应后再由对应模块解析成固定字段。如果模型返回空内容、非 JSON、字段不符合预期或供应商接口报错，AI 服务不会把异常内容透传给业务端，而是返回统一错误结构。这样业务服务可以清晰判断是模型不可用、请求超时、额度限制还是输出格式错误。

处方建议也是类似流程。业务端传入诊断、主诉、过敏史和院内药品目录，AI 服务只生成建议草稿，不直接创建正式处方。医生端拿到建议后，可以选择采纳、修改或放弃，再由处方业务接口创建正式处方。这个细节让 AI 在开药环节提供辅助，但最终处方责任仍保留在医生业务操作中。

### 4.2 RAG 知识库

`app/core/rag.py` 支持两套知识检索路径：

- 配置 `AI_RAG_DATABASE_URL` 时，使用 PostgreSQL + pgvector 持久化知识库。
- 未配置或允许降级时，使用内置规则知识源进行离线演示。

知识库重建会从业务库读取科室、医生、已发布排班、医生事件、医技项目和药品目录，并合并院内 AI 使用规则，写入 `ai.knowledge_document`。检索时使用向量距离排序，并可按来源类型过滤。

该设计使 AI 回答不只依赖通用模型，还能感知本院医生、排班、项目和药品数据；同时保留内置规则兜底，方便本地演示与异常恢复。

RAG 重建可以拆成一个具体流程：管理员或后端任务调用 `/api/ai/knowledge/reindex`，AI 服务先确保 pgvector 扩展、`ai` schema 和 `knowledge_document` 表存在，再从医生、药房等业务 schema 中读取有效数据。每条业务数据会被转换成知识文档，例如“某医生所属科室、职称、擅长方向”“某药品名称、规格、价格”“某医生某天某时段已发布排班”。系统为文档生成向量后写入知识库，并清理已经不存在的旧业务文档，避免删除的排班或药品继续被 AI 检索到。

医生推荐就是 RAG 数据参与业务的例子。患者描述症状后，系统可以结合科室信息、医生擅长方向、可用排班和号源背景生成推荐结果。这样推荐不是简单按关键词匹配科室，而是结合医院当天实际资源，体现了院内业务数据对 AI 输出的约束。

AI 排班建议则更强调运营数据。医生服务先整理需要重排的科室、诊室、日期、医生不可用时间、科室需求和历史挂号摘要，再调用 AI 服务生成建议。AI 只输出“某医生在某日期、某诊室、上午/下午出诊”的半天粒度建议，不直接生成分钟级号源；管理员确认发布后，医生服务再同步生成半小时粒度号源。这种流程把 AI 建议和正式排班发布拆开，便于管理员审核。

### 4.3 影像分析与人工确认

CT 分析模块包含 DICOM 转换、预处理、ONNX Runtime 推理、金属伪影分类、病灶检测、病灶分割、分类器和推理流水线。后端医嘱服务只保存 AI 长任务 ID 和结果 JSON，正式报告仍由医技医生确认。

该设计把耗时 AI 推理作为异步任务处理，避免阻塞医技业务接口；同时通过报告确认、任务超时、失败重试、来源标记和审计事件保证安全闭环。

影像分析内部可以进一步拆成“附件定位、格式转换、预处理、模型推理、结果汇总、报告草稿”几个小步骤。业务服务传给 AI 服务的是对象存储中的附件 key 和医嘱上下文；AI 服务负责读取或转换影像数据，完成模型推理后输出结构化结果。业务服务不会直接关心模型细节，只关心任务状态、模型版本、错误信息和最终结果。这种接口隔离使后续替换模型或增加新影像算法时，不需要改动医生工作台的主流程。

## 5. 数据库与基础设施设计

后端各服务使用 Spring JDBC 而非重型 ORM，Repository 层直接表达 SQL 查询和状态变更，适合当前业务流程明确、跨表查询多、状态机要求高的医院业务场景。

数据隔离采用 PostgreSQL 多 schema：

- `auth`
- `patient`
- `doctor`
- `appointment`
- `cashier`
- `medical_record`
- `medical_order`
- `pharmacy`
- `report`
- `audit`
- `ai`

各服务在 `src/main/resources/db/migration` 下维护 Flyway 迁移脚本。当前仓库中后端迁移脚本共 71 个，覆盖账号、患者、科室、医生、排班、号源、挂号、支付、退款、病历、医嘱、附件、报告、处方、药品、库存、审计和初始化演示数据。

基础设施选择如下：

- PostgreSQL：核心业务数据。
- pgvector：AI 知识库向量检索。
- Redis：认证/患者/医生/药房缓存。
- RabbitMQ：审计事件和异步通知式集成。
- MinIO：检查检验附件对象存储。
- Elasticsearch：药品与审计日志搜索增强。
- Docker Compose：本地开发环境一键启动。

## 6. 前端设计

工作人员端使用 Vue 3 + TypeScript + Pinia + Vue Router + Element Plus。`frontend/src/router/index.ts` 按角色配置工作台入口，并在路由守卫中检查登录态与角色权限。Axios API 模块按业务域拆分为 `auth`、`patient`、`doctor`、`appointment`、`medical-order`、`pharmacy`、`cashier`、`audit`、`ai` 等文件，与后端微服务边界基本一致。

患者端使用 uni-app + Vue 3 + Pinia，页面围绕患者完整就诊旅程组织。由于患者端需要运行在微信小程序环境，项目使用 `@dcloudio/uni-*` 生态，并通过 `build:mp-weixin` 生成小程序产物。

前端整体采用角色工作台模式，而不是通用菜单堆叠模式。每类用户打开系统后直接进入对应工作流，减少医院现场操作路径。
